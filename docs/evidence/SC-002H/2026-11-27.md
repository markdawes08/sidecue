## Procedure

1. Run the display inspection from the repository root. Launch the existing ignored `artifacts/sc-002c-local/LaunchSidecue.exe` via the Windows computer-use helper. The launcher exited after starting Sidecue. The helper reported no launcher window, then identified the new shell as its only Sidecue window.
2. Select **Show display** and read the UI Automation tree. Send Ctrl+Alt+Enter and check the focused element. Type the synthetic draft into the focused overlay and try to read the value and selection. The helper exposed the control and focus but returned no text value.
3. Use Ctrl+Alt+Escape to return to the shell. Select **Window details** and confirm the shell's tree contains both visible owned surfaces. Read the details window's capture-exclusion status. Invoke Ctrl+Alt+Escape again and recheck the tree and shell status. Close the test-owned shell and verify no new Sidecue window remains.
4. In the Desktop suite, start a synthetic WPF text composition against the real enabled textbox instead of assigning its `Text` property. Assert the exact result before the update and after the update.

Commands from the repository root in Windows PowerShell:

```powershell
powershell -NoProfile -File docs/evidence/SC-002C/inspect-displays.ps1
powershell -NoProfile -File tools/build.ps1
. .\tools\common.ps1
Invoke-SidecueDotnet @('test', 'tests/Sidecue.Desktop.Tests', '-c', 'Release',
    '--no-build', '--no-restore', '--logger', 'trx;LogFileName=sc-002h-desktop.trx',
    '--results-directory', (Join-Path $repoRoot 'artifacts\test-results'))
```

The first build overlapped the live app and exited 1 because it could not replace an in-use DLL (MSB3027 and MSB3021). After the test shell closed, the build exited 0 with zero warnings or errors. The Desktop suite exited 0.
